# Il gate rosso per una condizione pre-esistente fuori perimetro — il problema

> Il gate della review è una misura binaria sull'**intera area**, e un rosso che esiste già alla
> base, in un file che il diff non tocca, blocca la consegna — che non può né correggerlo (il
> contratto le vieta di scrivere fuori dalla lista) né procedere (gate rosso = `BLOCKED_NO_COMMIT`).
> Il costo è che un arretrato di lint in un repository ferma **ogni** consegna futura, e restituisce
> all'owner una worktree sporca da trattare a mano.
>
> **Area.** *contratti* (la regola vive in `skills/review` e `skills/ship-feature`) — e il suo
> verdetto è di *strumenti*: a fermare il commit è `architect/architect.mjs`, che va toccato perché
> la regola cambi davvero.
> **Contesto.** In questo repository `.docs/PUNTI-APERTI.md` **non esiste**, e non esiste alcun
> documento che abbia già deciso questo punto: il problema è nuovo. Le memorie pertinenti sono
> [[valutatore-deterministico]] (il verdetto vincola e il banco è l'unica difesa),
> [[guardrail-nascono-spenti]] (dove un divieto può avere una sede deterministica, ce l'ha sempre) e
> [[tre-livelli-di-parametro]] (il comando di gate è un valore di `.daiku/project.json`).
> **Stato:** analisi al 30 settembre 2026.

---

## In una riga

Il gate di un'area è un comando che copre **tutta** l'area e produce un booleano senza memoria: non
sa se il rosso l'ha portato il diff o se c'era già. Un `F841` di ruff in un file di test invariato
rispetto alla base rende `gate: "red"`, e `gate: "red"` produce `BLOCKED_NO_COMMIT` — deterministicamente,
in `architect/architect.mjs`. La consegna non può correggere quel file (il contratto le vieta di
scrivere fuori dalla lista dei file cambiati) e non può procedere: resta la worktree sporca, e il
lavoro esce dal pool finché l'owner non lo tratta a mano.

## Com'è fatto oggi

### Taglio A — i contratti del gate

**Il gate è una fase della review, sempre eseguita e una sola volta**, marcata *worker*:
`plugins/daiku/skills/review/SKILL.md:233` («### Gate — **worker** role, always») e `:235` («It
**always** runs, even at zero findings, and **only once** on exit: it is the real verification that
the delivered diff compiles and passes the tests»).

**La granularità è per area toccata, e il comando è quello dell'area intera**, non del perimetro né
del singolo file:

- `plugins/daiku/skills/review/SKILL.md:241` — «It runs **every touched area**, and only those. For
  each, in this order:»
- `plugins/daiku/skills/review/SKILL.md:244` — «2. Then the area gate: run `{areas.<area>.gate}` and
  report the real outcome of the commands, loading the touched modules to catch the errors
  manifesting only at import.»
- `plugins/daiku/contracts/project-contract.md:85` — «| `areas.<area>.gate` | the area's gate
  command: lint, format, type-check, test and package build |»
- `plugins/daiku/contracts/project-contract.md:192-193` — «> For each area declared in `{areas}`
  touched by the perimeter, run `{areas.<area>.gate}` and report the commands' real outcome. An area
  untouched by the perimeter is not run.»

**Qualunque esito non verde rende il gate rosso**, senza distinguere la causa:
`plugins/daiku/skills/review/SKILL.md:246` — «The cycle **does not reopen** after the gate: a red
blocks the commit. If the red comes from failed tests or a compile/import error, **do not invent a
fix**: report `gate: "red"` with the real output.» La forma del blocco è
`plugins/daiku/skills/review/SKILL.md:249` — `{"gate": "green|red", "gate_detail": "<actual outcome of the executed commands, never an unverified claim>"}` —
e il dominio in `plugins/daiku/schemas/blocks.json:60-67` è `"gate": ["green", "red"]`.

**Il perimetro che il gate può correggere è la lista dei file cambiati, e nient'altro.** Tre
punti:

- `plugins/daiku/skills/review/SKILL.md:237` — «**The file list is not the initial scope**: fixes and
  coverage may have added files. After coverage and its closing round, `action: "areas"` with `from:
  "base"` recomputes it […] in its prompt that `files` list, the touched `areas` with the
  `{areas.<area>.paths}`, `{areas.<area>.lint_fix}` and `{areas.<area>.gate}` the tool returned, the
  perimeter of what is licit for it to correct, and the block to return.»
- `plugins/daiku/skills/review/SKILL.md:243` — «1. **Valid only if `{areas.<area>.lint_fix}` is
  declared.** Lint pre-pass on only that area's files: run `{areas.<area>.lint_fix}` with `<FILES>`
  replaced, **as declared**, without adding flags […]»
- `plugins/daiku/skills/review/SKILL.md:246` — «Correct **only** what is lint/format in nature inside
  the list, and **only at unchanged semantics** […] if making lint pass required a behaviour-changing
  modification, **do not do it** — report `gate: "red"` with that detail.»

Verifica diretta sul codice del tool (fatta qui, col mio esito): la lista dell'area **non** contiene
file non toccati. `plugins/daiku/architect/ledger.mjs:280-284`:

```js
    const mine = changedFiles(cwd, from, to, codeRoot, paths).filter((file) => inScope.has(file));
    if (!mine.length) continue;
    const commands = {};
    for (const key of COMMANDS) if (isObject(area[key])) commands[key] = area[key];
    touched.push({ area: name, files: mine, commands });
```

`mine` è l'intersezione fra i file **cambiati** in quel range e lo scope. Un file invariato rispetto
alla base non entra mai in quella lista. (Una lettura di prima mano della § *Gate* lo lasciava
ambiguo; il codice lo scioglie.)

**Il gate rosso ferma il commit in due punti**, entrambi deterministici:

- `plugins/daiku/skills/ship-feature/SKILL.md:214` — «| `gate` ≠ `green` | `BLOCKED_NO_COMMIT` —
  blocker: `gate red: <gate_detail>` plus all blocking items |»
- `plugins/daiku/skills/review/SKILL.md:258` — «The answer is `commit`, or `stop` with `blockers`
  naming which of the six conditions stopped it: […] **a gate that is not green** […]»

E il contratto si difende dal giudizio dell'agente: `plugins/daiku/skills/ship-feature/SKILL.md:381`
— «| \"The gate is red but the code is clearly right, I commit\" | Red gate = `BLOCKED_NO_COMMIT`.
Classification is deterministic, not a judgement. |». Con una precisazione importante:
`plugins/daiku/skills/ship-feature/SKILL.md:132` — «For **Review** failure is **only** the absent
block, not `gate`: a `gate: \"red\"` is a successful measurement».

**Lo sblocco meccanico esiste, ma non copre questo caso.** `plugins/daiku/skills/ship-feature/SKILL.md:231`
— «It unblocks only when the cycle already said everything it knew how to say — converged exit
(`fixed-point`), empty `missing_disciplines`, no `blocking: true` item and empty `to_confirm`». E il
subagent che corregge è vincolato a «no behaviour change, no file outside the reported ones»
(`plugins/daiku/skills/ship-feature/SKILL.md:233`): cioè alla stessa lista di file cambiati. Un
secondo tentativo non è ammesso (`plugins/daiku/skills/ship-feature/SKILL.md:238` — «A single attempt
per delivery»).

**Una dichiarazione di rosso pre-esistente non ha una sede.** Nel blocco `review_outcome`
(`plugins/daiku/skills/review/SKILL.md:272-290`, 19 campi) gli unici che parlano del gate sono `gate`
(`green|red`) e `gate_detail`, quest'ultimo definito «actual outcome of the check on the touched
areas, one line» (`:282`). Non c'è un campo per l'origine dell'errore; la prosa del report
(`plugins/daiku/skills/review/SKILL.md:268` e il paragrafo `## Delivery` di
`plugins/daiku/skills/ship-feature/SKILL.md:328-329`) è l'unico posto libero, e non ha valore di
verdetto: nessuno la legge.

**Ricerca nell'intero pacchetto.** Le parole `pre-existing`, `preesistente`, `already red`,
`già rosso`, `verde alla base`, `at the base` **non compaiono mai in relazione al gate**. Le
occorrenze di `pre-existing` sono tutte un'altra cosa — il divieto per un *finder* di segnalare
difetti fuori dalle righe del diff: `plugins/daiku/skills/arch-check/SKILL.md:35`, `plugins/daiku/skills/code-review/SKILL.md:53`,
`plugins/daiku/skills/dead-code/SKILL.md:34`, `plugins/daiku/templates/project/instructions.md:42-43`.
Le occorrenze di `baseline` sono la base-ref congelata della review, mai una soglia verde/rossa del
gate: `plugins/daiku/skills/review/SKILL.md:3`, `:83`, `:85`, `plugins/daiku/architect/ledger.mjs:331`, `:456`.

### Taglio B — il valutatore e il ledger

Misura e decisione sono due programmi separati: `architect/architect.mjs` decide e **non apre nessun
file del progetto** (`plugins/daiku/architect/architect.mjs:11-14`), `architect/ledger.mjs` legge Git
e scrive il ledger (`plugins/daiku/architect/ledger.mjs:2-20`). Il gate entra nel valutatore **solo**
dentro il blocco `review_outcome`, come una coppia opaca.

**Cosa chiede ogni domanda** (`plugins/daiku/architect/architect.mjs:1149-1159`, verbatim):

```js
const REQUIRES = {
  decision: ['review_outcome'],
  closing: ['review_outcome', 'ledger'],
  unblock: ['review_outcome'],
  propagation: ['step'],
  resumption: ['entry', 'present', 'ledger'],
  order: ['entry', 'present', 'ledger'],
  round: ['ledger', 'rounds_cap'],
  layers: ['layers', 'added'],
  block: ['name', 'block'],
};
```

Nessuna delle tre domande che toccano il gate riceve l'elenco dei file cambiati: `decision` e
`unblock` prendono solo `review_outcome`, `closing` anche il `ledger`. Il dominio di `gate` è
`GATES = ['green', 'red']` (`plugins/daiku/architect/architect.mjs:177`, validato a `:252-254`).

**La chiusura: la condizione è `gate === 'green'`, senza guardare altro** —
`plugins/daiku/architect/architect.mjs:448-466`:

```js
    const conditions = [
      ['to_confirm items with blocking: true', blockingItems(out).length === 0],
      ['a detected oscillation', (out.oscillation || 0) === 0],
      ['an exit by rounds-exhausted', out.outcome !== 'rounds-exhausted'],
      ['missing disciplines', out.missing_disciplines.length === 0],
      ['a green gate', out.gate === 'green'],
      ['a ledger the commit can read', readableLedger(input.ledger)],
    ];
```

E `askDecision` (`plugins/daiku/architect/architect.mjs:402-437`) traduce `gate !== 'green'` nel
blocker `gate red: <gate_detail>` (`:406`) e quindi in `BLOCKED_NO_COMMIT` (`:424`).

**Lo sblocco meccanico: cinque condizioni, nessuna sulle origini del rosso** —
`plugins/daiku/architect/architect.mjs:468-484`:

```js
  const holds = [];
  if (out.gate === 'green') holds.push('the gate is not red, so the block is not the first row of the table');
  if (out.outcome !== 'fixed-point') holds.push(`the cycle did not exit at a fixed point, it exited by ${out.outcome}`);
  if (out.missing_disciplines.length) holds.push(`disciplines that did not run on this diff: ${out.missing_disciplines.join(', ')}`);
  if (blockingItems(out).length) holds.push('a blocking item remains');
  else if (out.to_confirm.length) holds.push('items to confirm remain, so the block is wider than the gate');
```

**Il ledger ha la misura che servirebbe, e non la usa.** L'azione `scope` scrive nel ledger
`scope_files`, l'elenco dei file cambiati dalla base, untracked inclusi
(`plugins/daiku/architect/ledger.mjs:489`, `:495`, `:472`). L'azione `areas` restituisce, per ogni
area toccata, i suoi file cambiati e i comandi dichiarati (`plugins/daiku/architect/ledger.mjs:562-578`).
Il contatore dei comandi è `const COMMANDS = ['check_fast', 'lint_fix', 'test_targeted', 'gate', 'coverage'];`
(`plugins/daiku/architect/ledger.mjs:256`), copiato per dichiarazione — **nessuna azione del ledger
esegue un comando di gate**: il suo esito entra solo come `gate: green|red` più `gate_detail` testo
libero, scritti da `tail` (`plugins/daiku/architect/ledger.mjs:759-760`) e validati contro lo schema,
che ammette solo i due valori (`plugins/daiku/architect/ledger.mjs:326`, `:335-341`).

Il punto che decide il problema: **nessun punto di `architect/` mette insieme «l'errore è in `X`» e
«`X` non è in `scope_files`»**. `readableLedger` non legge `scope_files`
(`plugins/daiku/architect/architect.mjs:440-446`), `REQUIRES` non passa alcun elenco di file a
`closing`, e l'unico posto dove un file è agganciato a qualcosa è `blockingItems`
(`plugins/daiku/architect/architect.mjs:417`), che legge `item.file`/`item.line` di un rilievo di
finder — non di un esito del gate. Un gate rosso non viene mai scomposto per file.

**Il banco non copre niente di questo.** I casi `closing` col gate sono
`closing:condition-gate-red` (`plugins/daiku/architect/architect.mjs:1381`) e
`closing:condition-rounds-truncated-does-not-block` (`:1396`); i casi `unblock` sono
`unblock:only-the-gate` (`:1401`) e i quattro che lo negano (`:1404`, `:1407`, `:1410`, `:1413`,
`:1416`); i casi `decision` col gate sono `decision:row-1-gate-red` (`:1340`, con
`gate_detail: 'tsc: 2 errors'`) e `decision:every-blocking-condition` (`:1361`). Tutti usano
descrizioni generiche e l'atteso dipende **solo** dal booleano `gate`. Nessuna fixture passa un
`ledger` con `scope_files` e un `gate_detail` che nomina un file fuori perimetro: la distinzione
pre-esistente/introdotto non è modellata né provata. `never_red`
(`plugins/daiku/architect/architect.mjs:2049-2070`, e `plugins/daiku/hooks/self-check.mjs:122-128`)
fa rosso un banco quando una regola non è mai stata vista fallire — ma vale per le regole scritte
via `rule()`, non per la semantica del gate.

### Taglio C — i parametri dell'area e il progetto ospite

**Le chiavi di un'area, verbatim da `plugins/daiku/contracts/project-contract.md:83-89`**:
`areas` (`:83`), `areas.<area>.paths` (`:84`, «the paths belonging to the area, each usable as a Git
pathspec»), `areas.<area>.gate` (`:85`, «the area's gate command: lint, format, type-check, test and
package build»), `areas.<area>.check_fast` (`:86`), `areas.<area>.lint_fix` (`:87`, «command applying
only safe lint fixes to the given files»), `areas.<area>.test_targeted` (`:88`), `areas.<area>.coverage`
(`:89`). Ogni chiave-comando ha forma `{ "cwd": <path>, "run": [<line>, …] }`
(`plugins/daiku/contracts/project-contract.md:48`), e `run` è una sequenza di righe che girano in
ordine, non alternative.

**Il segnaposto `<FILES>` esiste, ma non sul gate.** `plugins/daiku/contracts/project-contract.md:51-53`
— «**`<FILES>` placeholder**: if a `run` line contains it, the skill replaces it with the list of
files it is working on […] It is the only placeholder allowed inside a command.» Nello scheletro
`plugins/daiku/templates/project/project.json`, `<FILES>` compare in `check_fast` (`:45`), `lint_fix`
(`:49`) e `test_targeted` (`:53`) — **mai** in `gate` (`:39-42`), che è `"run": ["<the exact line to
run, not a description of it>"]`. La forma attuale non permette due comandi di gate per area: `gate` è
una chiave sola, con un solo oggetto-comando, e non esiste in tabella alcuna `gate_targeted` né un
`gate.files`.

**Un comando dichiarato che fallisce è un esito, non una chiave mancante.**
`plugins/daiku/contracts/project-contract.md:317-318` — «**A declared command fails**: it is a real
outcome, not a missing key. Report the output, do not look for an alternative command.»

### Il caso reale (esiti eseguiti il 30 settembre 2026)

La consegna della feature *supporto-ant* su ReforgIA (`C:/dev/ReforgIA`, progetto ospite) si chiude
`BLOCKED_NO_COMMIT` con **due** blocker: una voce di prodotto bloccante da confermare e il gate non
verde (`src/docs/nuovi-sviluppi/supporto-ant/5. review-report.md`, § 7).

Le mie misure, rifatte qui:

- `src/.daiku/project.json` dichiara per l'area `backend`: `gate` →
  `{"cwd": "apps/backend", "run": ["pnpm --filter @reforgia/backend check"]}`, `lint_fix` →
  `{"cwd": "apps/backend", "run": ["venv/Scripts/python.exe -m ruff check --fix <FILES>"]}`, `paths`
  → `["apps/backend/"]`.
- Lo script `check` di `src/apps/backend/package.json` è `pnpm run lint && pnpm run format:check &&
  pnpm run test`, con `lint` = `ruff check app tests main.py`: il gate copre **tutti** i file
  dell'area, test compresi.
- `git diff --name-only 8a037b1 -- src/apps/backend/tests/test_workspace_service.py` → **vuoto**: il
  file è invariato rispetto alla base.
- `venv/Scripts/python.exe -m ruff check tests/test_workspace_service.py` sul file così com'è
  (uguale alla base) → **esce 1**: `F841 Local variable \`repo\` is assigned to but never used --> tests\test_workspace_service.py:344:13`.
- Lo stesso comando dichiara che quel difetto **non ha un fix sicuro**:
  «Found 1 error. No fixes available (1 hidden fix can be enabled with the `--unsafe-fixes`
  option).» — cioè nemmeno `lint_fix` (`ruff check --fix <FILES>`), se il file fosse in lista, lo
  chiuderebbe.
- La terza causa è di formato: `format:check` vuole riformattare lo **stesso** file (dichiarato in
  `5. review-report.md` § 5).
- Il contesto della review: `outcome: "fixed-point"`, `missing_disciplines: []`,
  `independence: "intact"`, `oscillation: 0`, 20 correzioni applicate e 7 severe, `coverage:
  "tests-written"`, e nei 12 file in perimetro `ruff check` verde e `pytest -q` 3450 passed / 0
  failed (`5. review-report.md`, § 7). La worktree `agent-tree-4` (branch `worktree-agent-tree-4`,
  da `main` @ `8a037b1`) resta sporca e fuori dal pool.

Va detto per intero: in questo caso lo sblocco meccanico era **comunque** negato, perché la prima
condizione che lo nega è `blockingItems(out).length`
(`plugins/daiku/architect/architect.mjs:477`) e una voce bloccante c'era. Il problema del rosso
pre-esistente si vede qui nella sua forma pura, ma non è l'unica ragione del blocco di questa
consegna.

## Perché questo diventa un problema (i gap)

1. **Il gate non ha memoria della base.** Misura l'area intera in un istante e produce un booleano;
   non confronta ciò che il diff introduce con ciò che c'era prima
   (`plugins/daiku/skills/review/SKILL.md:241-246`, `plugins/daiku/architect/architect.mjs:457`). Un
   rosso pre-esistente e un rosso introdotto sono lo stesso valore.

2. **L'origine del rosso non ha né forma né sede.** `gate_detail` è prosa libera e illimitata
   (`plugins/daiku/schemas/blocks.json:60-67`), e nessun campo del blocco `review_outcome` né del
   report porta l'attribuzione (`plugins/daiku/skills/review/SKILL.md:272-290`). Verificato: le
   parole `pre-existing` / `already red` non compaiono mai in relazione al gate in tutto `plugins/daiku`.

3. **Il contratto vieta di trattarlo, e il tool glielo conferma.** Il gate corregge solo «inside the
   list» (`plugins/daiku/skills/review/SKILL.md:246`), e la lista contiene solo file cambiati
   (`plugins/daiku/architect/ledger.mjs:280-284`, verificato). Nel caso reale il file non ha un fix
   sicuro di ruff: la correzione richiederebbe una mano umana o un giudizio, non `lint_fix`.

4. **La conseguenza non è una consegna persa, sono tutte.** Il gate di un'area è lo stesso per ogni
   consegna futura: finché quel `F841` e quel formato restano, **ogni** delivery su quell'area
   finisce `BLOCKED_NO_COMMIT`. E ogni consegna bloccata consuma una worktree del pool
   (`plugins/daiku/skills/ship-feature/SKILL.md:240-242`).

5. **Il costo si scarica sull'owner.** Il blocco non produce una via d'uscita: la worktree resta
   sporca e dichiarata, il report la nomina, e «esce dal pool finché l'owner non la tratta»
   (`plugins/daiku/skills/ship-feature/SKILL.md:240`, e la coda di `5. review-report.md`). Il lavoro
   umano che Daiku doveva risparmiare torna indietro.

6. **Il dato per distinguerlo esiste già, in parte.** `scope_files` e `areas[].files` sono nel ledger
   e nella risposta di `areas` (`plugins/daiku/architect/ledger.mjs:489`, `:575`); le domande del
   valutatore non li ricevono (`plugins/daiku/architect/architect.mjs:1149-1159`) e `readableLedger`
   non li legge (`:440-446`). Non manca una misura da inventare: manca il collegamento.

7. **Il banco non prova nulla di tutto ciò.** Nessuna fixture passa un `gate_detail` che nomina un
   file e un `ledger` con `scope_files`: la distinzione non è modellata né verificata
   (`plugins/daiku/architect/architect.mjs:1381-1418`). Per [[valutatore-deterministico]], un caso che
   il banco non copre non è un verdetto sbagliato: è una consegna che si ferma.

## Trade-off e dubbi aperti

1. **Dichiarare e procedere, o dichiarare e correggere.** La prima forma tratta il rosso
   pre-esistente come non-difetto di ciò che si consegna, e il commit passa dichiarandolo. La
   seconda allarga il perimetro al file che porta il rosso e lo corregge a semantica invariata, con
   una sola soluzione ovvia. Sono opposte nel rischio: la prima consegna codice con un gate non
   verde (chi legge il report deve fidarsi della dichiarazione); la seconda fa scrivere — dopo
   l'ultimo finder — un file che nessun finder ha visto, che è esattamente la ragione per cui il
   divieto di scrivere fuori lista esiste (`plugins/daiku/skills/review/SKILL.md:246`).

2. **Chi misura l'origine: l'agente o il programma.** Il pacchetto ha già la distinzione
   «una misura che un agente esegue e riporta è una dichiarazione, una che esegue un programma è una
   misura» ([[valutatore-deterministico]]). La dichiarazione la può dare il gate subagent; la misura
   — «quel file è in `scope_files`? è cambiato dalla base?» — la può dare solo il ledger, che Git lo
   legge già (`plugins/daiku/architect/ledger.mjs:134-138`). Da sciogliere: se la regola nuova nasca
   come *dichiarazione* con un campo in più, o come *misura* con una domanda nuova del valutatore.
   La seconda ha un banco, la prima no.

3. **Qual è il criterio esatto.** La direttiva dell'owner parla di «rosso confinato ai test». Ma nel
   caso reale il rosso è duplice — un `F841` **e** una riformattazione — sullo stesso file, e il
   formato non è un test. I criteri candidati, da confrontare per misurabilità:
   - *fuori perimetro e invariato rispetto alla base* — misurabile col ledger, indipendente dal
     linguaggio e dalla forma del file;
   - *in un file di test* — richiede di sapere cos'è un test, e in un progetto Python un file di test
     è un path (`tests/`), in un altro è una configurazione;
   - *di lint/format e non di test o compilazione* — restringe ai difetti che non toccano la
     semantica, ma il gate non dice da quale stadio viene il rosso se non nella prosa di
     `gate_detail`.

4. **Cosa fare quando il rosso pre-esistente è nel perimetro, o introdotto dal diff.** Il confine
   nuovo deve dire chiaramente cosa **resta** bloccante: un rosso su una riga che il diff ha scritto
   è il difetto che il gate esiste per prendere (`plugins/daiku/skills/review/SKILL.md:246`).

5. **Quanto costa distinguerlo.** Stabilire che un rosso pre-esiste richiede di misurarlo **alla
   base**: o un secondo giro del comando di gate sull'albero di base — cioè il tempo della suite due
   volte, che è precisamente il costo che il gate, «only once on exit», esiste per non pagare
   (`plugins/daiku/skills/review/SKILL.md:235`) — oppure una via più stretta: guardare se il file
