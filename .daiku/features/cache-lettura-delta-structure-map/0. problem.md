# Ogni rilettura di un file paga il file intero — il problema

> Descrizione del problema, senza soluzione. Analisi dai documenti della corsa, **non** dal codice del
> pacchetto: l'indagine su `plugins/daiku/` per questo lavoro non è stata fatta.
> **Stato:** analisi documentale al 12 ottobre 2026. Fonte: la proposta della corsa *Compaction
> deterministica — euristica e locale* (2026-10-03),
> `.daiku/features/compaction-deterministica-euristica-e-locale/cache-lettura-delta-structure-map.md`,
> e la sintesi `.daiku/studies/compaction-deterministica-euristica-e-locale/sintesi.md`.

## In una riga

I subagent di Daiku rileggono gli stessi file molte volte — contratti, memorie, sorgenti nei giri
successivi di `/review` — e ogni rilettura paga il file intero, anche quando il file è cambiato di
poche righe o è un sorgente grande di cui serve solo la forma. Daiku non ha una cache di lettura.

## Come funziona oggi

**Il pacchetto non intercetta il gesto di lettura.** Fra gli hook cablati in
`plugins/daiku/hooks/hooks.json` — `PreToolUse` su `Bash|PowerShell`, su `Edit|Write|MultiEdit` e su
`AskUserQuestion|Agent|Task`; `PostToolUse` su `Edit|Write|MultiEdit` e `AskUserQuestion`;
`SessionStart`, `UserPromptSubmit`, `Stop` — non c'è nessun aggancio sul tool `Read`. Ogni lettura va
al file intero, e nessuna sede ricorda cosa è già stato servito.

**La rilettura è la norma, non l'eccezione.** Nel ciclo di Daiku lo stesso file rientra più volte
nella stessa consegna: un contratto o una memoria vengono aperti da più fasi, e nei giri successivi di
`/review` i sorgenti appena toccati si rileggono. È la stessa superficie che rende probabile la
compaction (vedi `sopravvivenza-compaction`), da un'altra porta.

**Il riferimento ha due modi e una disciplina di misura.** Da alexgreensh/token-optimizer (B3) la corsa
porta i due modi — il *delta* (un diff unificato quando il file è cambiato poco) e la *structure map*
(un scheletro di firme e import per un file codice grande) —, le guardie sul costo quadratico e
sull'estensione, e la modalità `shadow`, con cui si misura il guadagno **prima** di servire davvero la
sostituzione. La sostituzione cade sempre sul file intero quando potrebbe perdere informazione. Il
*come si costruisce* per esteso è nella proposta; qui non si ricopia.

**La cache è uno stato di sessione, e vive fuori dal progetto.** La proposta la deposita in un file di
sessione fuori dal progetto — la sede è la stessa decisione di quadro aperta per le altre feature
(vedi `frame-delle-feature-di-contesto`).

## Perché diventa un problema (le lacune)

1. **Nessuna cache di lettura.** Ogni rilettura paga il file intero, e nulla ricorda che quel file è
   già stato letto in questa sessione.
2. **Il costo è strutturale, non accidentale.** La rilettura è dentro il metodo: le fasi riaprono i
   contratti, la review riapre i sorgenti. Non è un caso raro da ottimizzare, è il modo in cui il
   ciclo funziona.
3. **Sostituire una lettura è toccare la verità che l'agente vede.** Servire un delta o uno scheletro
   al posto del file significa decidere cosa dell'agente può non vedere: un fallback incompleto è
   peggio del file intero.
4. **Il costo del parsing può superare il risparmio.** Uno scheletro che richiede un parsing pesante a
   ogni lettura, o un delta calcolato su file grandi, può costare più del file che sostituisce: le
   guardie sul costo quadratico e sull'estensione non sono un contorno.

## Trade-off e dubbi aperti

- **Delta e scheletro sono due risposte a due domande diverse.** Il delta risponde a «cosa è cambiato»,
  lo scheletro a «com'è fatto»: decidere quando vale l'uno e quando l'altro è parte del disegno, non
  un dettaglio.
- **Servire o misurare.** La modalità `shadow` — misurare il guadagno senza ancora sostituire — è
  coerente con la disciplina di Daiku (misurare invece che fidarsi), ma ritarda il risparmio: quanto a
  lungo misurare prima di servire è una scelta.
- **Quando una sostituzione perde informazione.** Il confine fra «il delta basta» e «serve il file
  intero» va determinato, non lasciato al sentimento.
- **Dove vive la cache.** Dentro la sede di sessione decisa dal quadro; ma una cache di lettura e un
  checkpoint di decisioni possono avere esigenze di durata diverse, e va visto se condividono la sede.

## Confine del problema (cosa NON è in scope qui)

- **Non si sceglie qui il meccanismo**: né la forma del delta o dello scheletro, né l'allowlist delle
  estensioni, né le soglie, né il modo di aggancio — decidono il documento delle decisioni e il
  disegno.
- **Non si decide la sede dello stato**: sta in `frame-delle-feature-di-contesto`.
- **Non è la compressione dell'output dei comandi** (`compressione-output-comandi`): là la superficie è
  l'esito di un comando, qui è il contenuto di un file letto.
- **Non è un problema di host**: non si tocca cosa un host offre oltre al tool `Read` già cablabile.
- **Non si toccano** gli hook esistenti né il loro banco.
